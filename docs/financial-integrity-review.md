## Fixes actually implemented

- `src/services/walletApprovalService.ts:decideDeposit/decideWithdrawal`: existing request ID is operation identity. One Serializable interactive transaction reads request and wallet, conditionally claims PENDING, mutates wallet, creates the existing real transaction row, and records authenticated admin audit. A failed ledger/audit write must roll back the whole operation. Conditional withdrawal debit requires balance >= exact Decimal amount. Rejection competes for the same claim.
- Same-decision retries have no additional financial effect. Approved replay requires exactly one correctly signed matching wallet/type/reference/amount ledger entry. Legacy missing/duplicate/mismatched entries fail for reconciliation; never fabricate or repair transactions. Opposite decisions reject. Serializable conflicts require explicit retry; no automatic financial retry loop. Current wallet balance on replay is not the original response balance.
- Existing deposit wrappers use the shared service; routes pass admin identity. Notifications happen only after successful new decision; failure is caught. Notification delivery is best effort, not durable/exactly once.
- Admin withdrawal action delegates status, debit, ledger and audit together, retaining required payment receipt. Approval records an administrative decision; it does not initiate or verify an external bank transfer.
- `walletService:chargeWallet` uses conditional sufficient-balance debit and Decimal comparison/signed ledger amount. This helper still lacks operation-level idempotency; withdrawal approval no longer uses it.
- `src/lib/historical-margin.ts:historicalMargin`: read-only Decimal calculation contract, no current-product fallback, unknown cost stays null, explicit projected/realized classification. It computes raw margin, including losses, and does not replace the existing clamped delivery-credit policy. It is not wired to production accounting because no snapshot exists. Its realized flag requires an independently verified caller; it does not prove settlement.

The request-row claim is an implemented application transaction boundary, not a database-wide ledger uniqueness constraint. **NOT IMPLEMENTED:** database-wide wallet atomicity/idempotency, real concurrency verification, all-writer available-funds enforcement. Legacy inconsistencies and out-of-band writers can still violate invariants. No simulated ledger was added to the application; test fixtures are synthetic and isolated.
