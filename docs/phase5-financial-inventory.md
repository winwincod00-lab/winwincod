New supplemental drafts: [loss model fragment](../proposals/phase5/loss.proposed.prisma) and [loss SQL design](../proposals/phase5/006_loss.proposed.sql). Review found that existing SELLABLE/DAMAGED dispositions do not represent loss. Loss is an evidence-backed write-off from transit or quarantine to external, never available stock. The supplemental SQL intentionally raises an exception before DDL; it is incomplete until operation closure, locks, conservation guards and ACL ownership integrate with the main proposal. The Prisma fragment is not an independently valid schema. No validation claim is made for this extension.

Loss rules: transit lost + delivered + physically returned cannot exceed shipped units. Quarantine loss + accepted + damaged cannot exceed physically received units. Quarantine loss is already within returned shipment quantity; do not double count it as transit loss. Require shipment/item, seller, quantity, evidence, actor, approved policy and stable operation key. Repeated observation is not proof of physical loss; carrier compensation and accounting recognition are separate evidence-backed operations. Later recovery requires a new linked receipt/correction, not editing loss history. Stage-test same/different-key duplicate write-off, receipt-vs-loss races, partial loss, unauthorized actors and no restock/refund effect.

### Transaction and retry design

Approval: inside SERIALIZABLE transaction authenticate current actor, bind tenant/request/payload, lock wallet and request in the agreed global order, verify existing financial evidence, claim unique business operation, change request, post exact signed cash event and balanced journal, update projection, append audit and close receipt. Deposit credit requires unique verified funding evidence. Rejection has no cash effect. APPROVED replay must verify original signed entry and receipt; mismatch stops for reconciliation. Never "repair" a missing legacy ledger by crediting again.

Withdrawal creation: server derives seller, claims seller/key/payload identity, locks wallet, validates immutable payout destination and available balance, creates request + HOLD + audit/receipt atomically. Approval consumes the whole active hold exactly once with unique confirmed payout evidence: balance and held both decrease, available stays unchanged. Rejection releases only an unsent hold. SENDING/UNKNOWN payout outcome keeps hold; resolve evidence before retry/release. External transfer is outside DB transaction with stable payout identity and outbox/worker state; do not repeat transport because a DB response was lost. Payout fees/partial payouts remain owner decisions.

For every debit, including batch payment, enforce available funds under the same locking contract. Financial operations use both tenant-scoped HTTP idempotency identity and unique business identity (deposit request, funding transfer, withdrawal/payout, batch payment or settlement entitlement). Same payload returns saved result; changed payload conflicts. Serialization/deadlock retry restarts the entire DB unit with the same keys and bounded jitter; no blind external-payment retry. P2002/uncertain commit recovery reads and verifies the durable receipt. Never claim these guarantees from mocked queues.

### COD/LIVCASH evidence mapping

Order + seller -> local shipment/item -> carrier account + stable local merchant reference -> carrier shipment/tracking identifier (if verified) -> statement + source row -> observed gross COD, fees, signed adjustments, net/currency -> bank remittance -> allocation -> approved wallet entitlement -> unique operation/journal/postings. Store carrier acceptance, delivery observation and bank receipt separately with timestamps/provenance.

Detect missing expected shipment settlement, unmatched carrier row, duplicate scoped row/reference, multiple candidate shipments, currency mismatch, unknown expected COD, COD mismatch, inconsistent `gross - fee + adjustment = net`, over-allocation and fee differences. A valid arithmetic MATCH is not settlement confirmation or bank evidence. Partial payments/returns require approved terms and manual review. Keep disputes unresolved rather than generating balancing payments. No new LIVCASH API, webhook, settlement endpoint or idempotency capability is assumed; obtain documentation/real sample statements through separately authorized work. An auditable manual import is acceptable if it meets the same evidence rules.
